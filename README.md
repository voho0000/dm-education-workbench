# 糖尿病衛教報告工作台

把一份健保申報 JSON 變成兩份報告：給病人的衛教報告，以及給醫療人員的摘要。

站台：<https://voho0000.github.io/dm-education-workbench/>

**併發症主題、個別化目標與追蹤間隔完全由程式依 R／PR 與指引門檻表判定，LLM 不參與。** LLM 只負責規則做不到的三件事，而它寫的每一個數值都會被逐一比對回原始紀錄。

## 這條流程長什麼樣

```
  ┊指引門檻表┊              健保申報 JSON
  ┊35條·附頁次┊        ┌──────────┴──────────┐
       ↓               ↓                     ↓
  確定性事實與判定                    LLM 好讀文字
  主題·目標·門檻（程式）               整理全部紀錄·數值照抄
       │                                    ↓
       │                               濾掉無關檢驗
       │                               微生物·血氣·白分類…
       ├──────────────┐        ┌──────────┼──────────┐
       ↓              └───────→│          │          ↓
  ① 資料稽核              ② 檢驗判讀      └───→ ③ 檢驗敘述
       └──────────────┬──────────┴───────────────────┘
                      ↓
                 驗證與組裝  ←  ┊固定衛教模組┊
                 數值比對·禁止事項  ┊已審·模型不改寫┊
                      ↓
            ┌─────────┴─────────┐
       病人版衛教報告        醫師版報告
```

三次呼叫互相獨立，任何一次失敗都只會少掉對應的段落，報告一定產得出來。**三者拿到的東西不一樣**：

| 呼叫 | 拿到什麼 | 做什麼 | 產出去向 |
|---|---|---|---|
| ① 資料稽核 | 只有確定性判定的結果 | 找資料的矛盾與需人工確認之處 | 醫師版最後一節；改不了任何程式判定 |
| ② 檢驗判讀 | 只有濾過的好讀文字 | 找程式門檻沒涵蓋的異常 | 醫師版；每個數值逐一比對回來源 |
| ③ 觀察摘要／短期建議／中期目標 | 兩者都拿 | 三段病人可讀的個人化內容 | 病人版；報告中唯一未經逐句核准的文字 |

### 原始 JSON 到送進模型之間有三層

頁面上三層都看得到，可以直接對照。只給最後一層的話，沒有人能判斷濾掉的是不是不該濾的。

1. **原始 JSON** — 使用者上傳或貼上的內容，一個字都不動
2. **LLM 好讀文字** — 整理成模型好讀的純文字，**數值照抄不改**
3. **濾掉無關檢驗** — 只有這一份會送給 ②③

第三層濾掉的是微生物培養（13007C）、藥敏（13023C）、細菌鏡檢（13006C）、輸血交叉配合（11002C）四個整碼，加上依項目名稱的血液氣體、白血球分類、發炎指標、凝血。實測五位病人 9,001 筆檢驗中佔 **30%**——這些 prompt 本來就叫模型忽略，送了再叫它不要看等於付兩次錢。

**不能整碼刪血液氣體**：09041B 底下藏著 K×49、Na×49、Hb×29、Glucose×29，整碼砍會連核心指標一起丟，所以那一類走項目名稱過濾。

**程式的判定不經過這道過濾**——`extractPatientFacts` 讀的是原始 JSON，濾錯也不會影響主題、目標與門檻判定。另外檢體品質旗標（溶血、脂血）與培養註解在事實抽取階段就排除，它們不是病人的測量值。

中期目標的**數字由程式從門檻表推出後餵給模型**，模型只負責寫成病人的話——讓模型自己訂目標值會失去可追溯性，也可能跟醫師版對不上。

① 原本叫「模組挑選」，要模型排出前三優先項。實測五位病人，接上與不接上它的輸出，兩份報告**逐字相同**——納入哪些主題由程式依 R／PR 判定，優先序改不了任何東西，而它真正抓到的資料矛盾（例如「基本資料標示慢性腎臟病：否，但 eGFR 最低曾達 22.8」）卻被程式丟棄。因此改成專職資料稽核，結果進醫師版。

## 病人版的六個段落

對齊健保署「115 年度智能衛教生成模組」要求的五大核心面向。個人化的內容排前面，模組型的通用衛教排後面。

| 段落 | 來源 | 對應面向 |
|---|---|---|
| 觀察摘要 | LLM ③ | (1) 觀察摘要 |
| 短期建議 | LLM ③ | (2) 短期建議 |
| 中期目標 | LLM ③（數字來自門檻表） | (3) 中期目標 |
| 併發症風險 | 固定模組 | (4) 併發症風險 |
| 預防叮嚀 | 固定模組 | (5) 預防叮嚀 |
| 什麼情況要立刻就醫 | 固定模組 | — |

## 本機啟動

需要 Node.js `>=22.13.0`。

```bash
npm install
cp .env.example .env.local
# 編輯 .env.local，填入 GEMINI_API_KEY
npm run dev
```

開啟 `http://localhost:3000`。預設模型 `gemini-3.6-flash`，可在頁面改。

## 資料與金鑰

不使用資料庫。病人資料與頁面輸入的金鑰只留在當前瀏覽器頁面，重新整理即清除。

**GitHub Pages 是純靜態版本，沒有後端**——金鑰由瀏覽器直接送到 Google Gemini API。金鑰不會寫入 repository、LocalStorage 或任何資料庫，但仍可能受裝置上的惡意瀏覽器擴充功能影響。請使用專用、受限、有限額度且可隨時撤銷的金鑰。

## 頁面上看得到什麼

- **管線**：每一站的材料、食譜、成品。食譜是用 `?raw` 讀真檔案再切出的函式，不是另抄一份說明——抄的那份會過時而沒有機制發現。
- **判定路徑**：這位病人的每一個主題判定，訊號在左（R／PR 值）、結果在右、理由在下。不納入的主題也保留（淡化顯示），因為「為什麼沒出現」和「為什麼出現」一樣需要看得到。
- **內容庫**：衛教模組、自我照護模組、指引門檻表逐條攤開，供醫療團隊審閱。三份都標 DRAFT。

### 開發時重現 API 失敗

dev 模式可用查詢參數模擬失敗，不需要真金鑰（正式建置不含這段程式碼）：

```bash
open "http://localhost:3000/?simulate=html"
```

可用值：`html`（代理層回 HTML 錯誤頁）、`400`、`404`、`429`、`slow`、`empty`。

Gemini 會間歇性對同一份輸入回 400「Request contains an invalid argument」——實測連送八次會掛一到兩次。`callGemini` 因此對這個特定訊息與 429／5xx 自動重試（最多四次、指數退避）；金鑰錯或模型錯同樣是 400，但不重試。

## 程式分層

病人可見的併發症與預防內容每一個字都由程式組合，LLM 不產生那部分正文。

| 層 | 檔案 | 做什麼 |
|---|---|---|
| 事實抽取 | `lib/patient-facts.ts` | 申報 JSON → 型別化事實。缺值一律 unknown，不補 0 |
| 檢驗值 | `lib/lab-findings.ts` | 項目名稱與醫令代碼映射、數值解析（保留 ≧ 等不等號）、安全門檻 |
| LLM 輸入整理 | `lib/format-patient.ts` | 整理成好讀文字並濾掉與糖尿病無關的檢驗類別；`skipIrrelevantLabs: false` 可取得未過濾版 |
| 門檻表 | `lib/guideline-rules.ts` | 35 條指引門檻，每條帶章表與 PDF 頁碼 |
| 目標推導 | `lib/resolve-targets.ts` | 依已發生併發症與年齡解出個別化目標；判不出來就說判不出來 |
| 目標比對 | `lib/target-comparison.ts` | 每一個有數值的指標都對照目標 |
| 主題判定 | `lib/module-plan.ts` `decideTopics` | 依 R／PR 決定納入哪些主題 |
| 模組文字 | `lib/education-modules.ts` `lib/self-care-modules.ts` `lib/shared-care.ts` | 固定文字 |
| LLM 解析與核實 | `lib/lab-llm.ts` `lib/lab-narrative.ts` | 解析三次回應，逐值比對來源、掃描禁止事項 |
| 組裝 | `lib/module-plan.ts` | 病人版與醫師版 |
| 驗證 | `lib/validate-report.ts` | 確定性檢查，可當作不會漂移的評分器 |

### 主題判定的規則

同一主題，來源只會給 R 或 PR 其中一個。R1–R7 就是 DCSI 的分項分數。

- R ∈ {1, 2} → 已發生，帶完整模組
- PR ∈ {1, 2} → 尚未發生，帶完整模組（預防內容）
- PR = 0 → 不納入
- R 與 PR 同時缺席 → 不納入（並列為資料異常）

### 檢驗項目比對的兩條規則

**名稱與醫令碼衝突時以名稱為準。** 實際遇過醫令開 09005C（空腹血糖）但結果列寫「飯後血糖 102」——名稱才是這一筆實際量的東西。這跟忠實搬運型的轉檔工具（相信申報碼、不重新詮釋）結論相反，因為用途不同：我們要拿這個值比對「空腹血糖 80–130」的目標，貼錯標籤就是對病人講錯話。有測試釘住。

**名稱窮舉一定會漏，能用醫令碼就用。** 同一個指標實測出現六種寫法（CRE、CRE(肌酸酐)、CREA、Creatinine、Creatinine(B)、Creatinine 肌酸酐），純靠名稱比對曾經 41 筆只抓到 20 筆，對兩位病人謊報「沒有肌酸酐紀錄」。血糖也踩過同一個坑（63 筆 Glu-AC 漏抓，導致報告寫「最低 68」而真正的最低是 20 mg/dL）。

腎臟主題有三條獨立的覆寫來源，因為它們可能同時漏掉同一位病人：來源 CKD 欄位、申報診斷碼、以及**檢驗證據**（eGFR < 60 或 UACR ≥ 300）。實測有病人 eGFR 最低 22.8 卻三項前提全缺。

## 端到端跑一次

```bash
node scripts/run-pipeline.mjs --patients <病人JSON目錄> --out <評估包目錄> [--selector <輔助判讀器輸出目錄>] [--only id1,id2]
```

產出可直接交給不懂這個 codebase 的人審查：原始資料整理版、程式抽取與判定、病人版報告、醫師版報告。`--selector` 沒給的話流程照樣完整，只是少了醫師版最後的資料稽核一節。

**產出含病人資料，請輸出到 repo 以外的位置。**

## 發布

只有一個部署目標：本儲存庫的 GitHub Pages。

```bash
npm run build && npm run export:pages
# 將 github-pages/dm-education-workbench/ 的內容放到 gh-pages 分支根目錄（含 .nojekyll）再推
```

站台由 `gh-pages` 分支根目錄提供。網址由 `PAGES_URL` 環境變數覆寫，只影響 `og:image` 的絕對網址；其餘資產都是 `./` 相對路徑，換路徑不會壞。`og.jpg` 由匯出腳本從 `public/` 帶進去——先前它只存在於 Pages 分支，`rsync --delete` 會把它清掉而社群預覽變 404。

舊網址 `voho0000.github.io/dm-education-report/` 留了轉址頁，在 `voho0000/voho0000.github.io` 儲存庫裡。

發布前確認 `git status` 沒有 `.env*`、指引全文或病人資料，且 `npm test` 全數通過。頁尾的 build 識別碼可用來確認線上版本是不是最新，而不是快取的舊版。

## 正式使用前

- 由醫療團隊核准三個 system prompt 與全部固定衛教內容。目前三份內容（衛教模組、自我照護模組、指引門檻表）**均為 DRAFT，未經核准，不得提供給病人**。
- 補上微量白蛋白尿（30–300 mg/g）的門檻規則。目前抽取出的門檻表沒有這個數字，腎臟主題因此接不到早期白蛋白尿。
- 明定病人資料截止日、報告有效期間及過期提醒。
- 不將歷史健保申報用藥描述為目前用藥。申報檢驗紀錄只有費用年月、沒有採檢日，因此報告全程不得宣稱時序（「最近一次」「已改善」「目前的數值」）。
- 糖尿病類型證據不足或衝突時，交由醫療團隊確認。
- 以批次測試、人工抽查與版本紀錄監控模型品質。
- 在部署環境中將 `GEMINI_API_KEY` 設為機密環境變數，不要寫入程式碼或提交到版本控制。
